# AI Knowledge

AIについて**活用する・選ぶ・構築する・理解する・追う／見通す**ための、根拠と更新履歴を持つ知識基盤。

一般的な用語解説を増やすことではなく、**読者の問いに最初から答え、必要な根拠や実践例まで一つの記事で辿れること**を目指す。独自の実験・制作経験・判断を重視しつつ、公式仕様などの基礎解説も必要な範囲で扱う。

## 読者の目的から探す

| 入口 | 何を知りたいか | 例 |
| --- | --- | --- |
| **活用** | AIを実際の作業でどう使うか | 複数エージェントの運用と実測 |
| **選ぶ** | 何を採用し、なぜ選ぶか | 予算に合わせたツール構成 |
| **構築** | 自分でどう実現するか | AI駆動開発環境の再現手順 |
| **理解** | 仕組みと判断条件は何か | MCPとCLIの使い分け |
| **追う・見通す** | 何が変わり、どう判断するか | 価格・利用上限の変化 |

入口は分類ラベルであり、記事のURLには含めない。記事は複数の入口に属してよい。

## 編集・検証の原則

- **第一文から答える。** 「比較が必要です」だけで終えず、条件・時点を明示した具体的な答えを書く。
- **一つの記事で完結する。** 前提・結論・根拠・制約・検証時点を確認できるようにする。
- **一般解説だけで終わらない。** 公式仕様、具体的な判断、一次情報、実験、実務の知見と結びつける。
- **事実と判断を区別する。** 公式情報、実測、経験、推論の出典を混同しない。
- **変化する情報を管理する。** データが複数の記事に登場する場合、正本を一つにする。ただし早期に抽象化しすぎない。

## まず5記事で検証する

判断・実験・手順・解説・見解の各1記事から始める。記事数を目標にせず、読み手の目的・自己完結性・根拠・更新の運用が成立するか確認する。具体的な候補と受け入れ条件は[Issues](https://github.com/rebuildup/ai-knowledge/issues)で管理する。

70本の候補とA〜Kの領域マップは**将来の候補・分類の材料**として扱う。詳細な内訳はこのリポジトリにまだ移植していないため、未確認の項目を仮に埋めない。

## 他リポジトリとの責務

- **このリポジトリ**: AI知識コンテンツ・根拠・メタデータ・更新管理の正本。
- [my-blog](https://github.com/rebuildup/my-blog): Qiita / Zenn / noteなどへの一般記事の公開管理。選択した記事のみ連携し、本文を二重に保守しない。
- [my-web-2026](https://github.com/rebuildup/my-web-2026): 個人サイト上の紹介・表示・導線。表示系の実装をここに混ぜない。

現時点では記事の表示アプリやCMSは実装しない。実際の5記事で必要性を検証してから決める。
