# 根拠と更新のルール

## 根拠の4分類

| 種類 | 何に当たるか | 記載する情報 |
| --- | --- | --- |
| **公式情報** | 公式ドキュメント、仕様、料金表など | 元URL、取得・確認日、適用条件 |
| **実測** | 自分で動かしたテスト・比較結果 | 対象環境、測定方法、日時、回数、生ログの所在 |
| **経験** | 実際の運用で起きたこと・失敗・工夫 | 利用状況と観察、一般化できない範囲 |
| **判断・推論** | 以上から導いたおすすめや解釈 | 何を根拠にどう判断したか、対案・制限 |

実際に測っていない数値を実測と呼ばない。公式出典があっても、そこから導いた主張は「公式が述べた事実」ではなく判断として分ける。

## 変動データを共通化する条件

価格・モデル・上限・対応機能などは、**複数記事で反復し更新頻度が高くなったとき**に `data/` を正本にする。最初から全てをYAML化する必要はない。

共通化した情報には少なくとも次を持たせる。

- **value**: 具体的な事実。通貨、地域、プラン、期間などの条件を含める。
- **source**: 確認した一次情報のURL。
- **verified_at**: その値を確認した日。収集時刻と検証の厳密さが異なる場合は分ける。
- **used_by**: 影響を受ける記事のslug。

値に変更があっても、影響記事の結論が自動的に正しくなるとは限らない。**記事を再検証する必要がある状態**として扱う。

## 更新方針

- **継続更新記事**: 根拠データや前提が変わったら、該当箇所だけでなく推奨・比較の結論も再検討する。最終検証日を明示する。
- **時点固定記事**: 当時の記録を保持する。後から誤りが判明した場合は訂正履歴・追記を残し、別時点の結果を混ぜない。
- **実験**: サンプル数・条件・生ログを可能な限り残す。少数の試行結果を一般的な性能差と断定しない。
- **公開先**: `my-blog`や個人サイトへ配信する場合、このリポジトリを本文・根拠の正本とし、コピー先で独立編集しない仕組みを検討する。

## 自動化を実装する順序

1. まず記事の検証日・出典と「更新が必要な理由」を手動で記録する。
2. 同じデータを複数記事で使い始めたら、共通データと依存記事を紐付ける。
3. 検証日が古い項目やデータ変更時の依存記事抽出を自動化する。
4. 自動更新された値を、そのまま「人間が判断を再検証した日」として記録しない。

証拠がない状態で記事に「最新」と書かないことが、更新頻度より重要。
