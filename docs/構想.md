# 構想・情報設計

## 目的

一般的なAIの用語集でも、特定ツールの販促ページでもなく、**読者が自分の課題に対する答えを根拠付きで得られる場所**を作る。

- **読者側の価値**: 第一文に答え、必要な前提、判断条件、根拠、検証時点まで記事内で確認できる。
- **書き手側の価値**: 実践・実験・判断を記録し、変動する情報を必要な範囲で再利用できる。
- **独自性**: 実測、失敗、採用・不採用の理由、制作経験、判断の検証可能性。
- **一般解説の位置づけ**: 記事の理解や判断に必要な場合は扱うが、既存解説の言い換えだけを目的にしない。

読者の対象範囲は将来に向けて広く保つ一方、初期制作は著者が一次情報を持つAI駆動開発・ツール選定・制作活用を優先する。

## 入口は読者の目的

1. **活用** — 作業・学習・制作でどう使うか
2. **選ぶ** — 条件に合うツールや構成は何か
3. **構築** — 自分で環境や仕組みをどう実現するか
4. **理解** — 仕組みと設計判断をどう理解するか
5. **追う・見通す** — 変化をどう把握し、今後をどう考えるか

入口はナビゲーションの見せ方であり、排他的なフォルダ分類ではない。タグ・記事型・時間の性質とは別の軸とする。トップページ・索引は最低限の導線から始め、記事の蓄積に応じて発達させる。

以前の構想にある**A〜Kの領域マップ**は残す方向だが、正確な各領域の定義と70本の候補はまだこのリポジトリに転記されていない。先に推測して固定しない。

## 情報の論理的な層

| 層 | 責務 | 例 |
| --- | --- | --- |
| **記事** | 問いへの答えを、独立して理解できる形で公開 | 判断、手順、解説、実験、見解 |
| **根拠・共通データ** | 公式仕様、実測値、価格など、結論の根拠を保持 | 価格の取得元、測定条件、実験ログ |
| **メタデータ** | 記事の型、入口、URL、対象時点、参照先を整理 | slug、type、time_policy |
| **保守** | 検証日、更新条件、依存記事の再確認を管理 | 価格更新から影響記事を抽出 |

**4層は責務の分離であり、必ず4システム・4リポジトリにするという意味ではない。** まずはMarkdownと必要なメタデータで成立させる。

## 情報設計とURLは分離

カテゴリーや5つの入口を変更しても記事のURLが変わらないよう、記事には安定したslugを付与する。URLは原則として `/<slug>` を想定し、`/build/<slug>` のような分類プレフィックスを必須にしない。

実際の公開URL・多言語対応・ルーティングは配信側の設計に合わせて最終決定する。ここでは、**同一記事に安定した識別子を持たせる**ことを先に定める。

## 初期に作らないもの

- 70記事の一括生成と、A〜Kの架空の穴埋め
- 実験前の過剰なCMS・検索・自動収集の実装
- 毎回読み替えが必要な硬直した記事テンプレート
- 同じ事実を複数の記事・リポジトリで別々に修正する運用

最初の5記事から具体的な困りごとを集め、拡張する。
