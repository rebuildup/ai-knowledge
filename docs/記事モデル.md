# 記事モデル

## 記事の型は5つ

| 型 | 読者の問い | 第一文で示すこと | 時間の扱いの例 |
| --- | --- | --- | --- |
| **判断** | 何を選ぶべきか | 条件と時点を含む推奨 | 最新推奨なら継続更新 |
| **手順** | どう実現するか | 到達できる完成形・対象環境 | 依存バージョン変化で再検証 |
| **解説** | なぜそうなるか | 定義・仕組みと重要なポイント | 仕様が変わった場合に改訂 |
| **実験** | 実際どうだったか | 観測結果と試験条件 | 原則時点固定、後日検証は追記・別記録 |
| **見解** | どう考えるか | 著者の主張と判断の範囲 | 原則時点固定。反証や訂正は明示 |

型は**第一文や構成を組み立てる道具**。記事を無理に5等分せず、混在する場合は主目的で1つ選ぶ。

## 時間の性質は別に記録する

記事型とは独立して、次のどちらかを指定する。

- **継続更新**: 現在の判断や手順を提示する。最終**検証日**と更新対象を明示する。単なるビルド日時を検証日にしない。
- **時点固定**: 当時の経験・測定条件・判断を保持する。誤記は訂正履歴を残し、新しい結果で当時の結論を黙って上書きしない。

例えば同じ「判断」型でも「今のおすすめ」は継続更新、「2026年10月当時の選定記録」は時点固定。

## 一記事の最低条件

1. **最初に答え**: 前提や注意だけで始めず、結論・結果・手順の到達点などを具体的に示す。未検証ならその旨を明記。
2. **対象条件**: どんな環境、予算、利用者、期間、バージョンに該当するか。
3. **根拠**: 引用元・実験条件・経験・推論のいずれかと、その限界。
4. **例外・適用外**: この結論が使えない条件。
5. **確認時点**: 公開日、検証日、実験日など、実際の意味が異なる日付を混同しない。

独立して読めることは、毎回同じ一般解説を長く再掲することではない。必要な定義を短く示し、詳細は信頼できる資料にリンクする。

## メタデータの仮仕様

実際の5記事で調整する。**この時点でCMS固有のフォーマットを確定しない。**

| 項目 | 意味 |
| --- | --- |
| `title` / `slug` | 見出し・安定した記事識別子 |
| `type` | 判断・手順・解説・実験・見解 |
| `entries` | 活用・選ぶ・構築・理解・追う／見通す（複数可） |
| `time_policy` | 継続更新・時点固定 |
| `published_at` | 実際の公開日（未公開なら空） |
| `verified_at` | 対象事実・手順・判断を最後に検証した日（未検証なら空） |
| `sources` | 記事内で根拠に使った出典 |
| `data_refs` | 共通データへの依存（存在する場合のみ） |

本文の更新日、ビルド日、情報の検証日を区別する。初期は記事Markdownのfrontmatter等で記述してよいが、正式スキーマは検証後に確定する。

## 記事を起こす順序

**結論 → 必要な根拠 → 適用条件 → 例外・制約 → 詳細**。第一文で言い切れないときは、測定や調査が不十分なのか、そもそも問いが広すぎるのかを確認する。
