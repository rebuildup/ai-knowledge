# 図版・ビジュアル方針

**図は装飾ではなく、文章だけより速く正しく理解できる情報を載せる。** 文字ばかりの長い記事を避けるが、画像枚数を増やすことを目的にしない。

## どの情報を何で見せるか

| 伝えること | 適した形式 | 避けるもの |
| --- | --- | --- |
| 選択肢の違い・判断分岐 | 条件図、比較表 | 情報量のないロゴの横並び |
| 入力から結果までの流れ | フロー図、構成図 | 長文を箱に詰めた画像 |
| 実際の使用・詰まった場所 | 必要箇所を切り抜いた実画面 | 無関係なストック画像、架空のUI |
| 数値の比較・変化 | 同一条件のグラフ、単位つき表 | 未測定の数値を絵で捏造すること |
| 操作手順 | 短いコード、コマンド、連続スクリーンショット | コピー不能なコード画像 |
| 抽象的な概念 | 箱・矢印による独自の模式図 | 役割が不明なAI風装飾 |

**画像でなければ伝わらないか**を先に考える。テキストでコピーしたいコマンドやJSONは画像化しない。

## 記事内の配置

1. 導入の結論は必ずテキスト。**意味のある最初の図**を、最初の判断分岐・構造説明・実験条件の付近に置く。
2. 図の直前または直後に、何を読み取るべきかを**一文**で説明する。「図のとおり」は使わない。
3. 1図につき原則**1つの問い**。図が細かくなったら文章・表・図を分割する。各段落に機械的に画像を入れない。
4. 実際の画像が未取得なら、見栄えのために作った偽スクリーンショットで埋めず、正確な模式図か本文を使う。
5. 本文中にただの `[画像を挿入]` を残したまま公開しない。必要な実画像が公開条件なら草稿のままにする。

## 視覚表現の原則

- **一貫性**: 図の文字組、余白、色の意味を揃える。現時点では無理にブランドカラーやサイト実装に固定しない。
- **可読性**: スマートフォンでも読める文字サイズ・余白。複雑な図は図を2つに分ける。背景色とテキストに十分なコントラストを取る。
- **アクセシビリティ**: Markdown画像に代替テキスト。図の要点は本文にも記載。色の違いだけで状態を表現しない。
- **元データを保持**: 構成図は編集可能なSVGなどのソースを残す。数値グラフは値・単位・実験条件を検証できるようにする。
- **写真・UI**: 本人が撮ったもの、利用を許諾されたものを優先。アプリ画面やログの個人情報・識別子・認証情報・内部URLを公開前に点検する。
- **生成画像**: 説明に必要なら利用可能。ただし実機画面、性能測定、実在するUIの証拠として生成画像を使わない。誤認のおそれがある場合は作例と明示。

## 制作フロー

1. **本文の問いと結論を確定**する。
2. 読者が理解しづらい概念を選び、図の仕事を1文で定義する（例：「CLIとMCPの操作境界を一目で示す」）。
3. 正確な図を作る。記事固有の素材は `articles/<slug>/assets/` に置く。使い回しが必要なら後から整理。
4. 本文からMarkdown画像として参照する（例は文章中の記法を示すだけで、実在するファイルではない）。説明・根拠を併記。
5. GitHubのMarkdownプレビューと、小さい画面での表示を確認する。GitHubへのコミットだけでは実際のサイトでの表示確認にはならない。

## 公開前のビジュアル確認

- 最初の図・表・コードが本文の主張の理解に役立つか
- 図版の位置・密度・順番が意味に合うか
- 画像が真実の実測や実画面を装っていないか
- 代替テキスト、資料の出典、必要な実測条件があるか
- 読めない小さな文字、巨大な縦長画像、意味のない写真で水増ししていないか

図版数・配色・縦横比を固定せず、**読者の問いに対して視覚が働いているか**で判断する。
