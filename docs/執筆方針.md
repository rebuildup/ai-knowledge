# 執筆方針：説明より、使える答えを

## 立場

**AIを過大評価せず、過小評価もしない。実際に使い、比較し、使える条件を示す。**

「最新」「無料」「無制限」「ローカルだから安全」といった特徴は、それだけでは採用理由にならない。機能、制限、効果、操作性、継続費用、再現性を条件付きで評価する。反対に、AIを使うこと自体を軽視せず、仕事がどう変わったかを具体的に扱う。

読者の知識量を決めつけない。初心者には前提の意味を短く示し、詳しい人には判断条件・失敗例・実測や一次資料を示す。読み手を煽らず、売り込まず、上から教えない。

## 文章の声

- **日本語の常体（「だ・である」基調）**。命令形より「〜すると」「〜なら」を用いる。製品固有の語は正しい表記を使い、曖昧な略語には初出で意味を添える。
- **最初の本文一文で読者の問いに答える**。一般論・問題提起・「本記事では」・時候の挨拶・TL;DRを先に置かない。
- **結論は条件付きで言い切る**。「どれでもよい」は避けるが、確かめていない優劣を断定しない。「未検証」の場合は答えられる範囲を正確に述べる。
- **短くする対象は読む時間**。文字数を減らすだけで例外・前提が失われるなら短くしない。不要な同義反復、冗長な背景、記事への誘導は削る。
- **独立して理解できる**。リンク先は補足・出典であり、結論を理解するために必須の「前編」にはしない。
- **中立を装わない**。著者の推奨・実験・見解は明示してよい。ただし比較根拠と採用しない場合の条件を同時に示す。

## 一段落の役割

基本は **答え → 適用条件 → 根拠 → 実際の使い方／制約**。毎回この見出しを置く必要はない。問いによっては表・コード・図だけで十分。

見出しは「何の話か」より「何を判断できるか」を優先する。段落には一つの主題を置き、見出し直後に同じ内容を言い換えるためだけの文章を足さない。

**書き方の違い**

| 避ける | 採用する |
| --- | --- |
| 「MCPはAIの可能性を広げる画期的な技術だ」 | 「既存CLIで目的を達成できるなら、MCPサーバーを増やす必要はない」 |
| 「料金、速度、制限などを比較しましょう」 | 「長時間使うなら、単発の料金より上限到達後の代替手段を先に確かめる」 |
| 「一概には言えないが、ケースバイケースだ」 | 「読み取り専用の定型処理ならCLIを選ぶ。ツール発見や実行契約の共有が必要ならMCPを検討する」 |
| 「実験した結果、驚くほど高速化した」 | 「同条件の比較ログがないため、高速化率はまだ示せない」 |

上の文は**文体の例示**であり、計測・実証済みの性能評価ではない。

## 型ごとに何を最初に書くか

| 型 | 第一文の契約 |
| --- | --- |
| 判断 | **対象条件と推奨**。どの条件で違う選択になるかも書く |
| 手順 | **到達できる状態と対象環境**。実機未検証ならそのことを明示 |
| 解説 | **仕組みから導ける実用上の結論**。用語の辞書的な説明だけで始めない |
| 実験 | **観測結果と条件**。未実施の場合は実験計画を「結果」のように書かない |
| 見解 | **主張と対象時点**。予測を確定事実として扱わない |

## 主張の精度

- **公式情報**：公式資料にある事実を扱う。引用日・対象バージョン・参照先を添える。
- **実測**：条件、試行回数、ログ、集計方法が確認できる場合だけ「測った」と書く。
- **経験**：実際の事例を示す。「自分の環境では」と「一般に」は分ける。
- **判断・推論**：推奨の基準、反例、確度を示す。
- **未確認**：空欄を想像で埋めず、公開前の確認事項として管理する。

文章・図・タイトルすべてに同じ基準を適用する。**未公開草稿を「完成記事」と見せない。**

## 記事が読者に提供するもの

- 「理解」なら、定義以上の**区別と使い分け**。
- 「選ぶ」なら、条件付きでも**具体的な判断**。
- 「構築」なら、再現できる**手順と成功判定**。
- 「活用」なら、作業例・得られた結果・**失敗を含む制約**。
- 「追う・見通す」なら、現在確かめられる事実と著者の**解釈の境界**。
